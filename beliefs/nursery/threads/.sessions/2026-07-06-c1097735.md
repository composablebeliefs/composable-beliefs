## Linking: tags outbound, anchors inbound, one predicate to reconcile

- **Test to prescription**: an ExUnit tag convention, `@tag verifies: "cb:b053"`. Colocated, zero ceremony, and `mix test --only verifies:...` falls out for free. A sweep test (same shape as the CLAUDE.md drift gate) asserts every tag resolves to an **active** prescription - a tag pointing at a superseded belief is staleness extended into the suite, which is what keeps links from rotting.
- **Prescription to test**: a `code:test/cb/schema_contracts_test.exs#...` anchor added as a dated evidence entry via `mix cb.evidence` - the sanctioned growth point, no schema change, and `CodeLocator` already turns a renamed test into a maintenance signal. `mix bs show cb:b053` then shows where enforcement lives.
- **Closing the loop**: a `prescriptions_test_backed?` predicate routed through the existing `CB.Method.Checks` machinery, so it runs inside `mix cb.verify.collection` with no new subsystem. The scoping decision matters most: only prescriptions that *claim* mechanical backing (an `enforcement:exunit` tag) are gated - most doctrine is held by judgment, and demanding universal linkage would force junk tests.
- **What results must not become**: per-run `cb.evidence` entries. That's the b386 digest antipattern - cached greenness. Run history belongs on `materialized` via `Sink.Test` (replace-on-rerun, as `cb.verify.codepath --record` already does); liveness is answered by running the suite.

## The DSL: extend by exactly one tier

The graph already describes tests at three depths - contracts interpreted directly (deepest, most successful), routing-in-data with `params` as test parameters, and whole suites as collections/corpora. The natural extension connects to the previous review: the `check` function proposed for the untested CLI surface is literally an interpreter for tests-as-data, so a `{"when": {"verify": "feature"}}` rule tier can carry cases (`argv`, fixture, golden path) on the very prescription that mandates the behavior. Equally important is where the DSL stops: algorithmic edge cases stay in plain ExUnit (linked by tag, never migrated - graph authoring ceremony on the activity that must be frictionless would violate the friction principle), the params schema stays one case-shape, and bulky corpora stay on disk with the graph holding one grounding prescription, not one belief per case. The rule of thumb: **the DSL describes a test when it discharges a named commitment and reduces to input-to-expected-output; everything else is ExUnit, linked by tag.**
