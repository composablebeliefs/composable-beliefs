## What each one actually is

Both projects build a graph about code so that AI agents can reason across sessions, which is why they rhyme so strongly on the surface. But their ontologies are opposites:

- **GitNexus builds a derived graph.** Tree-sitter parses the code, resolution connects imports/calls/inheritance, Leiden clustering finds communities, and heuristics trace "processes" (named execution flows). Every node is mechanically extracted, disposable, and regenerable on the next index run. It answers *what the code structurally is*.
- **cb builds an asserted graph.** Every node is a claim someone (human or agent) chose to make, grounded in an artifact, immutable, superseded rather than re-derived. It answers *what we believe about the code, why, and on what evidence* - including things no parser can extract: decisions, rationale, prescriptions, "this is the intended invariant."

One telling contrast: GitNexus puts a 0-1 confidence score on every edge; cb bans confidence scores outright. But it's not actually a head-on collision - GitNexus's scores are deterministic resolution-certainty from parsing, whereas cb's rule (per the CLAUDE.md and the schema beliefs) targets *subjective scores synthesized without a deterministic basis*. GitNexus's confidence is closer to cb's "specific evidence" than to the vibes-based scoring cb rejects.

## Where they compete

They compete on exactly one surface: **feeding code context to an agent via deterministic tooling** (GitNexus's 17 MCP tools vs. `mix bs` / `mix cb.*`). If you tried to use cb to represent code structure itself - functions, call edges, dependencies - GitNexus wins without contest. cb's code anchoring is a literal-substring grep (`code:path#anchor@N`, resolved line-by-line with `String.contains?` in `lib/cb/anchor.ex`); there is no AST, no symbol table, no call-graph extraction, and everything is hand-authored. cb also has a real gap GitNexus directly covers: `mix bs stale` only detects *belief-dependency* staleness. Nothing detects when anchored *code* drifts - a moved anchor silently resolves to its new line, and a rewritten line that still contains the substring gives no signal at all.

## Where they're complementary

The complementarity is clean because each is blind where the other sees:

1. **GitNexus as an evidence oracle for cb.** GitNexus can't say why anything is the way it is; cb attestations can cite GitNexus query output (`trace`, `impact`, `context`) as the artifact grounding a structural claim. Derived facts stay in the disposable layer; only claims worth standing behind get minted.
2. **Anchor-drift detection.** GitNexus's `detect_changes` maps git diffs to affected symbols/processes. That's precisely the missing input for "which cb `code:` anchors and codepaths need review after this commit" - a code-facing sibling of `mix bs stale --cascade`.
3. **Codepath authoring assistance.** GitNexus derives the actual call chain from an entry point; a cb author currently reconstructs it by hand before narrating it.

## Codepaths and GitNexus: yes, directly related

GitNexus's **"process"** concept (a named, traced execution flow like LoginFlow, grouped from entry points through call chains) is the derived twin of a cb **codepath** (entry step, ordered stops, branch choices). Same shape, opposite provenance:

- A GitNexus process is *computed* and can't be wrong in an interesting way - if the code changes, you re-index and get the new truth.
- A cb codepath is *curated and falsifiable*: each stop carries a prose claim that can be false, and contract-grade stops route to inspection-only predicates that run as a real test suite (`mix cb.verify.codepath`). Per the design rationale in cb:b467, the codepath is a teaching and commitment artifact, not a structural index.

So a codepath adds exactly what a derived trace can't (narration, claims, verifiable commitments), and a derived trace provides exactly what codepath authoring lacks (the ground-truth chain, drift detection).

## Recommendation: conjunction, not parity

Don't absorb GitNexus's scope. Reaching parity means multi-language tree-sitter parsing, import resolution, community detection, embeddings, and hybrid search - a huge orthogonal engineering effort, and one that fights cb's own design commitments: an immutable provenance graph is the wrong home for regenerable derived facts (you'd be superseding thousands of nodes per commit to track what a re-index gives you for free). cb's design center is the epistemic layer; GitNexus's is the structural layer.

The right split is layered: GitNexus (or something like it) as the disposable derived substrate, cb as the durable asserted layer on top, with attestations citing derived query output as evidence. That said, two *narrow* ideas are worth absorbing rather than outsourcing, because they harden cb's own primitives:

- **Sturdier anchors** - even minimal symbol-aware anchoring (or storing a content fingerprint of the anchored line in evidence) would fix the silent-drift failure mode without importing an AST pipeline.
- **A diff-to-anchor staleness check** - a `mix cb.stale --code` sibling that walks `code:` artifacts against the git diff since each belief's evidence date. Deterministic, no parsing needed, and squarely within cb's existing verify-tooling idiom.

Everything beyond that - call graphs, processes, semantic search - is better consumed from a tool like GitNexus than rebuilt inside the belief graph.

Is there any advantage to imagining porting gitnexus to elixir? Could composable beliefs as the asserted layer experience a deeper level of interop with the derived substrate if that substrate is itself written in elixir?

## Assistant

This is a question where the honest answer is: a full port buys you very little, but a *narrow* Elixir-native derived substrate buys you something real - and for a specific reason that has nothing to do with GitNexus itself.

## Why porting GitNexus wholesale is a bad trade

GitNexus's value is not its plumbing; it's the accumulated language-specific resolution logic - 15 languages of import resolution, receiver-type inference, `self`/`this` handling, framework pattern extraction. That heuristic corpus is the moat, and a port means rewriting all of it against a weaker ecosystem: tree-sitter bindings for Elixir exist but are immature NIF wrappers, there's no embedded graph database comparable to what GitNexus uses, and there's no Leiden community-detection library on the BEAM. You'd spend the effort where Elixir is weakest (polyglot parsing infrastructure) to replicate features cb doesn't need in-process (embeddings, hybrid search, clustering - those serve LLM retrieval, not belief verification).

And the headline justification - deeper interop - mostly doesn't require same-language. The relationship between the asserted and derived layers is *evidential*: cb cites derived query output as artifacts grounding attestations. That interface is file-and-JSON shaped and deliberately arms-length, and the arms-length quality is a feature, not a limitation. An external, disposable substrate can't tempt anyone into blurring the layers by computing "beliefs" on the fly, and a CLI invocation with its output is a citable, reproducible evidence reference in exactly the way cb's provenance model wants.

## Where same-runtime interop is genuinely deeper

There are exactly two places in cb's architecture where the derived layer being in-process (rather than behind a subprocess) changes what's structurally possible:

1. **Codepath predicates.** The predicate gate (`lib/cb/predicate_gate.ex`) requires zero-arity, in-process, inspection-only boolean functions - that contract is the whole safety story per cb:b045/b050. A predicate can't cleanly shell out to an external indexer; it would make the verify suite depend on an external tool's installation and freshness. But if a derived symbol/call index lives in the same BEAM, predicates like `anchor_still_inside_named_function?` or `codepath_stops_form_real_call_chain?` become legal, deterministic, in-process inspections. That upgrades codepaths from "narration plus hand-written checks" to "narration whose structural spine is machine-checked."

2. **Anchor resolution.** `CB.Anchor.resolve/2` is substring grep today. Same-runtime symbol spans would let it confirm an anchor still sits inside the symbol it was minted against, and let a `mix cb.stale --code` sibling detect drift deterministically - closing the silent-drift gap identified last turn without marshaling every resolution through a subprocess.

## The point that actually decides it: Elixir analyzes Elixir for free

Here's the asymmetry that makes an Elixir substrate attractive on its own terms. GitNexus needs tree-sitter plus heuristic resolution because it's parsing 15 languages from the outside. Elixir code doesn't need any of that machinery to be analyzed *from the inside*: `Code.string_to_quoted/1` gives you the real AST, compilation tracers observe every remote call as the compiler resolves it, and `mix xref` already produces caller and dependency graphs. For Elixir codebases you get compiler-verified call edges - effectively confidence 1.0, which sits better with cb's rejection of synthesized confidence scores than GitNexus's probabilistic edges do. GitNexus scores edges because heuristic cross-language resolution is uncertain; the Elixir compiler just knows.

And cb's primary dogfooding target - the self-describing graph anchored into `lib/cb/` - is an Elixir codebase. So a "GitNexus-for-Elixir-only" substrate built on xref and compiler tracers is maybe five percent of the porting effort, with *higher* fidelity than GitNexus achieves, covering the codebase cb most needs it for.

## What I'd actually imagine

Not a port. A small Elixir-native derived layer - symbol table, spans, static call edges from xref/tracers - living as a library cb can call in-process, its index treated like `.gitnexus/`: regenerable, gitignored, never written under `beliefs/`, since an immutable provenance graph is the wrong home for facts a re-index reproduces. It feeds exactly the two deep-interop points above (anchor verification, structural predicates) and nothing more. For polyglot host repos, keep GitNexus or its like at arm's length over CLI/MCP, cited as evidence the same way any external source is.

The layering stays philosophically clean either way: the derived substrate answers "what is," cb answers "what we stand behind." Same-language doesn't deepen that relationship in general - it deepens it only where cb's own contracts (in-process predicates, the anchor resolver) forbid crossing a process boundary. Those two points are real, they're the ones worth building for, and they need about a twentieth of GitNexus, not a port of it.
