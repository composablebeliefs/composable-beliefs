## What a wholesale shift would lose

- **Grounding.** Prescriptions carry `deps` and dated evidence; cb:b059 requires every active one to ground in something. Issues carry prose links that nothing verifies. The "why" chain — the thing that lets a fresh session follow a desk item back to the records that justify it — has no GitHub equivalent.
- **Provenance integrity.** This repo just spent real effort (cb:b573, cb:b587) protecting commit SHAs as citation targets, disabling squash/rebase merges because GitHub's own affordances silently break content-addressed references. Issues are worse on this axis, not better: bodies are silently editable, comments deletable, edit history host-dependent. As evidence artifacts they're weak.
- **Deterministic, offline session start.** "A session resumes from the graph" works because the desk query is pure local traversal. An issues-based desk requires network, auth, and an API — and this very session runs in an environment where GitHub access goes through MCP with scoped permissions. Concurrent sessions in restricted environments would lose the desk entirely.
- **The b386 trap.** The tempting migration path — mirror prescriptions into issues, or keep both in sync — is exactly the procedural-freshness cache b386 calls an antipattern, and cb:b384 already flags drift audits as the cost of any materialized copy. Two sources of truth for the backlog is the worst outcome.

## The seam already exists

The architecture anticipated this: `/materialize` turns a prescription into concrete work items via a **pluggable sink** (`CB.Materializer.Sink.JSON` is just the default), and the belief's `materialized` field records the link so it's never double-materialized. A GitHub Issues sink is a small, natural extension. That gives a clean division of labor with one-way truth flow:

- **Prescription** = durable intent: grounded in deps, immutable, what the house stands behind. Contracts, conventions, standing policies stay here unconditionally.
- **Issue** = the ticket materialization of that intent: mutable, collaborative, closed by the PR that discharges it, citing the belief id in its body for the "why."
- **Outcomes flow back** via `/assert`, cited by commit SHA (stable) rather than issue URL (mutable).

For pure tickets with no durable intent behind them, you could go further and mint the issue directly, skipping the graph — the test being "does this node do any work after it's closed?" That would let the graph concentrate on what composes.
