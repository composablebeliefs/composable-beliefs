## What the current setup conflates

There's also the immutability tax: rescoping a ticket-as-prescription takes supersession ceremony that an issue absorbs with an edit and a comment. So for that class of node, GitHub issues are genuinely a better fit — mutable scope, assignment, PR cross-linking, close-on-merge, and visibility to collaborators who will never run `mix bs`.

## What a wholesale shift would lose

- **Grounding.** Prescriptions carry `deps` and dated evidence; cb:b059 requires every active one to ground in something. Issues carry prose links that nothing verifies. The "why" chain — the thing that lets a fresh session follow a desk item back to the records that justify it — has no GitHub equivalent.
- **Provenance integrity.** This repo just spent real effort (cb:b573, cb:b587) protecting commit SHAs as citation targets, disabling squash/rebase merges because GitHub's own affordances silently break content-addressed references. Issues are worse on this axis, not better: bodies are silently editable, comments deletable, edit history host-dependent. As evidence artifacts they're weak.
- **Deterministic, offline session start.** "A session resumes from the graph" works because the desk query is pure local traversal. An issues-based desk requires network, auth, and an API — and this very session runs in an environment where GitHub access goes through MCP with scoped permissions. Concurrent sessions in restricted environments would lose the desk entirely.
- **The b386 trap.** The tempting migration path — mirror prescriptions into issues, or keep both in sync — is exactly the procedural-freshness cache b386 calls an antipattern, and cb:b384 already flags drift audits as the cost of any materialized copy. Two sources of truth for the backlog is the worst outcome.

## The seam already exists

The architecture anticipated this: `/materialize` turns a prescription into concrete work items via a **pluggable sink** (`CB.Materializer.Sink.JSON` is just the default), and the belief's `materialized` field records the link so it's never double-materialized. A GitHub Issues sink is a small, natural extension. That gives a clean division of labor with one-way truth flow:

- **Prescription** = durable intent: grounded in deps, immutable, what the house stands behind. Contracts, conventions, standing policies stay here unconditionally.
- **Issue** = the ticket materialization of that intent: mutable, collaborative, closed by the PR that discharges it, citing the belief id in its body for the "why."
- **Outcomes flow back** via `/assert`, cited by commit SHA (stable) rather than issue URL (mutable).

For pure tickets with no durable intent behind them, you could go further and mint the issue directly, skipping the graph — the test being "does this node do any work after it's closed?" That would let the graph concentrate on what composes.

So the end-state taxonomy for dev work would be:

- **"Do X"** → GitHub issue, closed by the PR. Git history is the evidence of work — no graph node, ever. No bespoke sink, no `/materialize`, no `cb.todo.close` for dev work. This satisfies your convention point: issues used exactly as issues.
- **"We haven't settled X"** → proto-belief document (or discussion), as now — but the document no longer needs a prescription-pointer to exist. Its *resolution* is what mints a node.
- **"X must hold"** → prescription, contract-grade where possible, minted when behavior settles — often at completion, not before. The graph stops being a backlog and becomes a spec-of-record. Provenance still binds it to git (`commit:` artifacts, `Belief:` trailers already exist for this), so "why does this behavior exist" survives without any ticket node.

Two honest caveats:

**Not every desk item is a ticket.** A handful encode decisions rather than work — b495 "decide the consensus direction," b503 "settle the reference convention." Those aren't issues either; they're deliberation, and they'd live in the proto-belief lane until resolution mints a convention. So the desk dissolves three ways, not two — but nothing needs to stay behind as a backlog node.

**The one genuine loss is preflight on intake.** Desk items currently get tag-overlap/conflict review at mint time (several carry evidence entries recording exactly that review). Issues get no adjudication against the contract layer. I'd argue this is a good trade: conflict-checking tickets against each other was low-value ceremony, and the high-value check — new *behavior claims* against existing contracts — survives intact, because behavior claims remain prescriptions and still go through preflight. The check just moves from intake-time to settlement-time, which is when the claim is actually stable enough to check.

The consequential part is that this obsoletes standing doctrine, not just data: the desk query itself (the lifecycle:discrete convention, the session-start "resume from the graph" prescription that compiles into CLAUDE.md via b586), `/materialize` for dev use, and the 30 open items needing homes as issues before their nodes retire. But as a position, I think you've landed somewhere more coherent than where the graph currently stands: git remembers what happened, issues track what's pending, and the graph asserts only what must remain true.
