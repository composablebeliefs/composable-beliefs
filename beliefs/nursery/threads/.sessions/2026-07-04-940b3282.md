**Where:** `2026-07-03-end-skill-round-trip.md` regions at lines 145, 213 (`cb:b518`), 176/247/263 (`transcript-format`), 889 (`cb:b573`); spec claim at `route-tagging.md:44-48`.

Two threads discussing the same matter necessarily emit the same string."* The routed-to column of this thread's table contains only: `end-skill-redesign`, `skills/end/SKILL.md`, `docs/operations.md`, `cb:b583`, `cb:b584`, `cb:b577`, `mint-manifest-rename`, `graph-refounding`, `vocabulary-read-surface`.

If future taggers do the same, the cross-thread join the spec promises is not guaranteed (one thread could tag `cb:b518`, another `end-skill-redesign`, for the same discussion).

**Why it matters:** this is the spec's core design claim, and its first instance already refutes it. It is not merely stale; it shows the "controlled vocabulary = routed-to column" invariant is unenforced and, in practice, unfollowed.

**Suggested fix:** either (a) enforce that every ref must appear in the thread's routed-to column - which would require adding routing rows for `cb:b518`/`transcript-format`/`cb:b573` or dropping those refs; or (b) honestly weaken the spec's claim from "cannot drift" to "should be drawn from the routed-to column where one exists" and specify what happens when a paragraph feeds an artifact with no routing row.

### Finding 2 (high) - The cb:b386 defense is overclaimed; the materialized log reintroduces procedural staleness
**Where:** `route-tagging.md:69-85` ("There is no cache to refresh - only an append log").

The spec's argument is sound for *block content* (a quote of a frozen thread never changes). But it overstates the conclusion. The materialized log's *completeness* depends on the `/decompose` append actually happening at every future route-time. A forgotten append yields a document that silently omits a later thread's discussion, presented as the complete cross-thread history - which is precisely cb:b386's harm ("stale... read as authoritative by subsequent sessions"). The dependency on procedural enforcement (remember to append) is the same property b386 condemns; "additive-only" changes the failure from *wrong content* to *missing content*, it does not remove the procedural dependency.

A second drift path the "frozen source" argument misses: because appended blocks are "write-once and never revisited," any later **correction to the tags** (this audit will likely prompt re-tagging per Finding 1) will **not** propagate to the already-materialized logs. The tags are the source of truth; the logs are a write-once cache that cannot be corrected without manual re-materialization. That is a concrete tag-vs-log divergence.

Note the thread itself conceded this: at `2026-07-03-...:163` the assistant called the CLI-live-render "the cb:b386-faithful version," and the materialized form was chosen over it for GitHub readability (`:215`). The spec should present this as the **readability-vs-freshness tradeoff it is**, not as fully b386-clean.

**Suggested fix:** soften the spec's prose to acknowledge the residual exposure (forgotten append; un-propagated tag correction), and state the mitigation honestly - e.g. a verifier that re-derives the log from tags and flags divergence (`mix cb.verify.*`), which restores the structural, not procedural, guarantee b386 asks for.

### Finding 4 (medium-high) - The spec documents a syntax its own retrofit abandoned, and the two forms render differently
**Where:** spec `route-tagging.md:37` and `:109` use `<p routes="...">`; the retrofit and the 2026-07-04 thread use `<routes ref="...">` throughout.

The spec's normative design block shows `<p routes="route-tagging statement-provenance">`, and its Open item frames the syntax question as "`<p routes="...">` vs comment fences" - never mentioning `<routes ref>`. Yet the actual demonstration ships `<routes ref="...">` (different element name *and* different attribute name). The spec was never updated to match its first instance.

This is not cosmetic. `<p>` is on GitHub's HTML allowlist, so `<p routes="...">` is **not** stripped - it renders as a paragraph wrapper (and cannot legally contain the multi-paragraph, multi-block regions the retrofit tags). `<routes>` is unknown and **is** stripped. So the readability behavior the retrofit claims ("sanitizer strips unknown tags, clean prose") is true only for the form the retrofit used, and **false for the form the spec documents**. The retrofit implicitly discovered `<p routes>` was wrong and switched, but left the spec asserting the abandoned, worse-behaving syntax.

**Suggested fix:** update `route-tagging.md`'s design block and Open item to `<routes ref="...">`, record why `<p routes>` was rejected (renders as a visible `<p>`, illegal block nesting), and keep the comment-fence alternative as the remaining open option.
